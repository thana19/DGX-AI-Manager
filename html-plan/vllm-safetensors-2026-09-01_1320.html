3 ข้อเท็จจริงที่ verify แล้ว

  • 1. โครงสร้าง repo จริง
    Qwen/Qwen3-8B-FP8 = safetensors ล้วน 12 ไฟล์ 9.45 GB ไม่มี .gguf เลย (HF API ?blobs=true)
  • 2. config.json มีทุกอย่างที่ต้องใช้
    architectures: ["Qwen3ForCausalLM"] · model_type: qwen3 · max_position_embeddings: 40960 · quantization_config.quant_method: fp8
  • Load-bearing 3. max_position_embeddings อาจซ้อนใน text_config
    โมเดล NVFP4 ที่รันอยู่บนเครื่องจริง (~/models/nvfp4/qwen3.8-27b-nvfp4/config.json) มีค่าอยู่ที่ text_config.max_position_embeddings = 262144 ไม่ใช่ระดับบนสุด ⇒ parser ต้องดูทั้งสองชั้น
  • Load-bearing 4. รายการไฟล์ตรงกับที่ vendor curate ไว้เป๊ะ
    ไฟล์ที่ vendor curate ไว้ใน catalog.yaml:106-117 = ไฟล์ทั้ง repo ยกเว้น .gitattributes และ README.md — เทียบกับ HF API ของ unsloth/Qwen3.8-27B-NVFP4 แล้วตรงกันเป๊ะ ⇒ ใช้กติกาจัดกลุ่มนี้ได้เลย
  • 5. ไฟล์ MTP ตรวจได้ก่อนดาวน์โหลด
    โมเดลที่มี MTP มีไฟล์ model_mtp.safetensors จริงในโฟลเดอร์ (NVFP4 มี · FP8 ไม่มี) ⇒ ตรวจ MTP จากรายชื่อไฟล์ได้ก่อนดาวน์โหลด
  • 6. ฮาร์ดแวร์รองรับ FP8
    เครื่องเป็น GB10 compute capability 12.1 (Blackwell) — FP8 e4m3 รองรับในระดับฮาร์ดแวร์

4 การตัดสินใจสำคัญ

#1
config.json คือแหล่งของ arch/ctx ของ safetensors — ยิง .../resolve/main/config.json ตรง ๆ · parser อ่าน architectures[0], model_type, max_position_embeddings ทั้งระดับบนสุดและใน text_config
เป็นแหล่งเดียวที่มีข้อมูลจริง · การซ้อนใน text_config เจอจริงกับโมเดลที่รันอยู่ (ข้อเท็จจริง #3)
#2·3
1 repo safetensors = 1 quant group · key มาจาก quantization_config.quant_method (ไม่มีก็ใช้ BF16) · ไฟล์ที่รวม = ทุกไฟล์ ยกเว้น .gitattributes, README.md, LICENSE*, *.md, ไฟล์ภาพ
root-level repo ไม่มีทั้งโฟลเดอร์ย่อยและ token quant ในชื่อไฟล์ · กติกาการคัดไฟล์ตรงกับที่ vendor curate ไว้เอง (ข้อเท็จจริง #4)
#4
model_mtp.safetensors ต้องอยู่ในกลุ่มหลัก ห้ามถูกจับเป็น companion
companion_kind() เห็นคำว่า mtp แล้วจะแยกออกเป็น draft ซึ่งเป็นกติกาของ llama.cpp (-md) · vLLM ต้องการไฟล์นี้อยู่ในโฟลเดอร์โมเดล
#7
เพิ่มฟิลด์ใหม่ตัวเดียว: ModelEntry.engine_env: dict[str, str] | None — main.py เอาไป env.update() ก่อนเรียก engine script
ModelEntry เป็น extra="forbid" เพิ่ม field ไม่ได้ถ้าไม่ประกาศ · ตัวเดียวครอบคลุมทั้ง parser/MTP และรองรับ engine อื่นในอนาคต ไม่ต้องเพิ่ม field รายตัว
#8·9
engines/vllm.sh สร้าง flag ตาม env แบบมีเงื่อนไข — ใช้ ${VAR-default} (ไม่มี colon) เพื่อแยก "ไม่ได้ตั้ง" กับ "ตั้งเป็นค่าว่างเพื่อปิด" · default ของ MTP ยังคง "เปิด" ตามเดิม (${VLLM_SPECULATIVE-mtp})
แก้จุดอ่อน 1+2 พร้อมกัน โดยไม่พึ่งสมมติฐานที่ยังไม่ verify ว่า argparse ของ vLLM ให้ flag ท้ายชนะ · พี่หนุ่มเลือกไม่แตะพฤติกรรมของโมเดล NVFP4 ที่ใช้งานได้อยู่ — ห้ามใช้ ${VAR:-default} เด็ดขาด
#10
เลือก tool-call parser ตาม model_type ด้วยตารางแม็ป (qwen3/qwen3_5, llama, mistral, deepseek_v3) · ตระกูลที่ไม่รู้จัก = ไม่ใส่ parser เลย
พี่หนุ่มเลือก "รองรับทุกตระกูล" · เดา parser ผิดอันตรายกว่าไม่ใส่ เพราะ request ที่มี tools จะ 400/500 ทั้งหมด

6 ไฟล์ที่แก้

ไฟล์สิ่งที่ทำประมาณการ
server/hf.py เพิ่ม fetch_config(), group_weights(), ฟิลด์ format ใน QuantGroup, ตารางแม็ป parser · ไม่แตะ group_quants() เดิม ปานกลาง
server/main.py resolve แยกสองทาง · response เพิ่ม engine/format/requires/engine_env · env.update(entry.engine_env) ตอน activate ปานกลาง
server/catalog.py ฟิลด์ engine_env ใน ModelEntry · is_ready() folder เข้มขึ้น เล็ก
engines/vllm.sh flag แบบมีเงื่อนไขจาก env + --max-model-len จาก CTX เล็ก
server/static/index.html payload builder แยกตาม format · carry requires/engine_env · แสดง format/engine ในตาราง · เตือนเมื่อไม่มี parser · แก้บั๊ก resolveRepoId ปานกลาง
tests/ + tests/fixtures/ fixture safetensors ใหม่ + test ตามหัวข้อทดสอบ ปานกลาง

7 ทดสอบแค่ไหน

  • unit test + regression ของเส้นทาง GGUF เดิมต้องผ่านครบ — ไม่แตะ group_quants() เดิม repo GGUF ต้องตอบเหมือนเดิมเป๊ะ
  • ทดสอบจริงถึงหน้า resolve เท่านั้น — ยิง resolve จริงกับ repo safetensors จริง ยืนยัน arch/ctx/format/engine ที่ได้
  • ยังไม่ดาวน์โหลด/activate จริง — เพราะกระทบพอร์ต :8000 และ llama.cpp ที่ลูกค้าใช้งานอยู่จริงบน :8001
